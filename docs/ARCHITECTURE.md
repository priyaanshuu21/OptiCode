# OptiCode architecture

OptiCode is a visual mini compiler. It runs MiniC through a real compiler pipeline and
returns **every stage's output** in a single JSON document, so the web UI can visualize
real compiler results rather than illustrations.

Central design rule: **every visualization is rendered from real compiler output, and
every optimization is provably semantics-preserving or is skipped with a recorded
reason.**

---

## 1. Pipeline

```
Source → Lexer → Tokens → Parser → AST → Semantic Analysis (symbols, types)
       → TAC lowering → Basic Blocks → CFG → Data-flow Analyses
       → Dead/Unreachable analysis (findings + explanations)
       → Optimization passes (events, stats) → Optimized IR/CFG
       → AST edits → Optimized source (+ interpreter verification)
```

| Stage | Package | Main output |
|---|---|---|
| Lexer | `opticode.lexer` | `Token[]`, diagnostics |
| Parser | `opticode.parser` | `Program` AST, unparser |
| Semantic | `opticode.semantic` | Symbol table, typed AST |
| TAC lowering | `opticode.ir` | `IRProgram` → `IRFunction[]` → `Instruction[]` |
| TAC invariants | `opticode.ir` | `InvariantViolation[]` (structural checks) |
| Blocks / CFG | `opticode.cfg` | `CFG`, `BasicBlock`, `Edge` |
| Interpreter | `opticode.ir.interpreter` | `ExecutionOutcome` (the semantics oracle) |
| Data flow | `opticode.analysis` | `FunctionAnalysis` per function: liveness, reaching defs, constants, def-use chains |
| Dead/unreachable | `opticode.analysis` | `AnalysisReport` of `Finding`s |
| Optimizer | `opticode.optimizer` | `OptimizationResult` (events, skipped, stats) |
| Source generation | `opticode.codegen` | `optimized_source`, change map |
| API | `opticode.api` | FastAPI app, Pydantic schemas |

Arithmetic and formatting rules live in exactly one place, `opticode.semantics`, and are
shared by the constant folder and the interpreter so the two can never disagree.

## 2. Package layout

```
backend/opticode/
├── compiler.py      # stage registration + compile_source() facade
├── core/            # SourceSpan, Diagnostic, Pipeline (no compiler knowledge)
├── lexer/
├── parser/          # AST, recursive-descent parser, serializer, unparser
├── semantic/        # symbols, types, analyzer, format checks, serializer
├── semantics/       # arith + format: single source of execution truth
├── ir/              # TAC model, lowering, printer, interpreter
├── cfg/             # basic blocks, edges, reachability, linearize
├── analysis/        # solver, lattice, liveness, reaching defs, constprop, results,
│                    # findings (dead/unreachable code)
├── optimizer/       # pass manager, passes, events
├── codegen/         # AST edits, optimized source, change map
└── api/             # FastAPI app + schemas
```

The frontend is stateless: no database, no sessions, no server-side cache.

## 3. Cross-cutting invariants

Every task must respect these.

1. **Spans everywhere.** Every token, AST node, and instruction carries a
   `SourceSpan` (1-based line/column, end exclusive). Instructions additionally carry
   `ast_node_id` and per-operand `operand_origin_ids`.
2. **Lowering never duplicates code.** Every source expression is lowered exactly
   once, so each operand occurrence maps to a single AST node. Optimized source is
   regenerated by editing the AST, never by decompiling TAC.
3. **Stages are pure.** No global state, no I/O, no network, no clock-dependent
   results. Identical input yields byte-identical output.
4. **Diagnostics, not exceptions.** User errors never raise. Each stage returns
   `(result, diagnostics)`. An unexpected internal bug becomes a structured
   internal-error diagnostic with no stack trace.
5. **Partial results are returned.** The pipeline stops after a stage that produced
   errors, but everything earlier stays in the response so the UI can still show
   tokens after a parse error.
6. **Deterministic IDs.** `n#` AST nodes, `i#` instructions, `B#` blocks, `t#` temps,
   `L#` labels, `d#` definitions, `f#` findings, `o#` optimization events. Preserved
   instructions keep their original ids in optimized IR.
7. **Optimizations act on proven facts only.** Every decision is recorded as an
   `OptimizationEvent`; every refusal is recorded as a `SkippedOptimization` with a
   reason.
8. **No compiler logic in the frontend.** The UI renders backend data and does layout.
9. **Synthetic instructions are invisible.** Implicit end-of-function `return`s are
   flagged `synthetic` and never reported to the user.

## 4. Data contracts

### 4.1 `SourceSpan`

```python
SourceSpan(start_line, start_col, end_line, end_col)  # 1-based, end exclusive
```

### 4.2 `Diagnostic`

```python
Diagnostic(severity, code, message, span, stage, related[])
```

* `severity`: `error | warning | info | hint`
* `code`: stable identifier, formatted `E-LEX-001`, `W-SEM-002`, `E-INT-001`, …
* `stage`: `input | lexer | parser | semantic | ir | cfg | analysis | optimizer | codegen | internal`

### 4.3 Request

```json
{
  "source": "int main() { return 0; }",
  "mode": "analyze",
  "options": { "passes": null, "max_iterations": 20, "include_unreachable": true },
  "stdin": ""
}
```

### 4.4 Response

```json
{
  "success": true,
  "mode": "analyze",
  "diagnostics": [],
  "tokens": [ { "type": "int_kw", "category": "keyword", "lexeme": "int",
                "value": null, "span": { ... } } ],
  "ast": { "id": "n1", "kind": "Program", "span": { ... },
           "semantic_type": null, "attrs": {},
           "children": [ { "role": "function", "node": { ... } } ] },
  "timings": { "tokens": 0.42, "ast": 0.31 },
  "stages_run": ["tokens", "ast"],
  "stages_skipped": []
}
```

Each stage field (`tokens`, `ast`, `semantic`, `ir`, `cfg`, `dataflow`, `analysis`,
`optimization`, `codegen`) is present **only if that stage ran**. A missing field means
the stage was skipped, and `stages_skipped` says why. `ast` is `null` when the parser
recovered from errors but built no tree at all; a partially parsed program still gets
its partial tree.

`dataflow` is keyed by function name and carries, per function:

```json
"f": {
  "name": "f",
  "instructions": { "i3": { "liveness": {...}, "reaching": {...},
                             "constants": {...} } },
  "live_in":  { "B1": ["x"] },   "live_out":  { "B1": [] },
  "reaching_in": { "B1": ["UNDEF(x)"] },
  "reaching_out": { "B1": ["x@i1"] },
  "branches": [ { "instruction_id": "i2", "operand": "t1",
                  "value": { "kind": "const", "value": 1, "type": "int" },
                  "statically_decidable": true, "always_taken": "B2" } ],
  "chains": { "uses_of": { "x@i1": [["i3", 0]] },
              "defs_of": { "i3#0": ["x@i1"] } },
  "uninitialized_reads": ["i3#0"],
  "exit_values": { "x": { "kind": "const", "value": 5, "type": "int" } },
  "iterations": { "liveness": 4, "reaching": 5, "constant_propagation": 6 }
}
```

`uninitialized_reads` lists every read whose only reaching definition is `UNDEF`, as
`"instruction#operand"`. A read that reaches both `UNDEF(v)` and a real write is **not**
listed: on that path the value is defined, and only the other path is indeterminate. It is
the static counterpart to the interpreter's `uninitialized_reads`.

`analysis` is one object rather than a per-function map, and carries the findings for every
function:

```json
"analysis": {
  "findings": [
    { "id": "f:dead_assignment:n9", "kind": "dead_assignment",
      "severity": "warning", "function": "f", "block": "B1",
      "message": "the value assigned to `x` is overwritten before it is read",
      "explanation": "`x` is reassigned here, so the value written on line 1 ...",
      "action": "will_be_removed",
      "span": { "start_line": 1, "start_col": 5, "end_line": 1, "end_col": 6 },
      "evidence": [ { "span": {...}, "note": "`x` is reassigned here" } ],
      "instruction_ids": ["i1"], "ast_node_id": "n9",
      "kept_reason": null, "duplicate_of": null }
  ],
  "summary": { "dead_assignment": 1 },
  "unreachable_blocks": [],
  "dead_instruction_ids": ["i1"],
  "finding_count": 1
}
```

`kept_reason` is present only on a finding whose action is `kept`, and `duplicate_of` only
when the semantic stage already reported the same fact.

### 4.5 AST

AST nodes are frozen, slotted dataclasses that all inherit from `Node`:

```python
Node(id, span, semantic_type)
```

The node's `kind` is its class name, taken by the serializer rather than stored. `id` is
the deterministic node id, `span` is the `SourceSpan` the node covers, and
`semantic_type` holds the type the analyzer inferred (`None` for statements and for
nodes from a program that never reached analysis).

| Node | Key attributes | Children |
|---|---|---|
| `Program` | — | `function` |
| `FunctionDecl` | `name`, `return_type` | `param`, `body` |
| `Param` | `name`, `type_name` | — |
| `Block` | — | `statement` |
| `VarDecl` | `name`, `type_name` | `init` |
| `Assign` | `target` (a plain name), `op`, `sugar` | `value` |
| `If` | — | `condition`, `then`, `else` |
| `While` | — | `condition`, `body` |
| `For` | — | `init`, `condition`, `update`, `body` |
| `Return` | — | `value` |
| `Break` / `Continue` | — | — |
| `ExprStmt` | — | `expr` |
| `Printf` | `format`, `format_span` | `argument` |
| `Scanf` | `format`, `format_span` | — (targets are name strings) |
| `BinaryExpr` | `op` | `left`, `right` |
| `UnaryExpr` | `op` | `operand` |
| `IntLiteral` / `FloatLiteral` / `StringLiteral` | `value`, `lexeme` | — |
| `Identifier` | `name` | — |
| `CallExpr` | `callee` (a plain name) | `argument` |

Design points that later tasks depend on:

- **A single child table.** `_CHILD_FIELDS` in `opticode.parser.ast` maps each node type
  to `(role, field)` pairs. Serialization, traversal, id assignment, and node cloning all
  read that one table, so they cannot drift apart.
- **Ids are assigned once, in pre-order.** `assign_ids()` numbers the tree `n1`, `n2`, …
  starting at the `Program`. `walk()` yields nodes in that same order, so id order and
  traversal order agree, and a later pass can rebuild a node while keeping its id.
- **Optional children are omitted, not nulled.** A `while` with no condition child
  serializes with no `condition` entry rather than an explicit `null`, which keeps the
  shape stable for the frontend.
- **Desugared nodes are first-class.** `a += e` and `a++` become ordinary `Assign` and
  `BinaryExpr` nodes carrying `sugar`, so later passes handle one form and the unparser
  can still reproduce the original text.
- **The unparser is the inverse of the parser.** `parse(unparse(tree))` has the same
  shape as `tree`, modulo source layout. Blocks stay blocks, so braces are never invented
  or dropped.

### 4.6 Semantic result

```python
SemanticResult(program, diagnostics, symbols, functions, bindings, scanf_targets, ok)
```

* `symbols`: serializable table. Each entry carries `name`, `ir_name`, `type`, `kind`
  (`param` | `local` | `function`), `scope_id`, and the declaration `span`.
* `bindings`: AST node id → `Symbol`. Lowering reads this instead of re-resolving names,
  because by the time it runs the analyzer's scopes have already been popped.
* `scanf_targets`: AST node id → target `Symbol`s, in source order, so each `read`
  instruction maps back to the variable it fills.
* `ok`: true when the bag holds no errors. Warnings leave `ok` true.

Every declared name gets a unique `ir_name` — the source name, or `name_N` when the name
is reused in a nested scope — so two TAC variables never collide even when both come from
`i`.

### 4.7 TAC

```text
x = y            (copy)          t = a op b       t = op a
t = itof a       t = ftoi a      label L:
goto L           if_false a goto L                 t = call f(a, b)
call f(a, b)     print "fmt", a, b                 read x
return a         return
```

```python
Instruction(id, opcode, dest, operands, target, span, ast_node_id,
            operand_origin_ids, synthetic, type)
IRFunction(name, params, return_type, instructions, declared_locals)
IRProgram(functions)
```

`uses()`, `defs()`, `has_side_effects()`, and `may_trap()` are derived from the opcode,
not stored, so they cannot disagree with the instruction itself. `may_trap()` is true for
`div` and `mod` unless the divisor is a nonzero literal constant.

Lowering rules that later passes depend on:

* Expressions lower post-order into temps; a literal or variable operand is referenced
  directly rather than copied first, so `if (0)` becomes `if_false 0 goto L`.
* `&&` and `||` lower to control flow writing a 0/1 temp, so the right operand is not read
  when the left one already decides the result.
* `for` lowers to init, condition label, `if_false`, body, continue label, update, `goto`
  condition, end label. `break` targets the end label and `continue` the continue label —
  not the condition, since `continue` must still run the update.
* A condition is **not** narrowed to `int`. A float condition is compared against zero, so
  truncating `0.5` to `0` first would invert the test. The same holds for `&&` and `||`.
* Each `scanf` argument becomes exactly one `read`; each `printf` becomes one `print`.
* A declaration with no initializer emits nothing. It is listed in the function's
  `declared_locals` instead, because it is live from function entry while having no
  defining instruction — dataflow seeds it as defined rather than inferring that from the
  instruction list.
* Every non-void function ends with a synthetic `return 0` so TAC is total; a caller never
  falls off the end of a function body.

### 4.8 CFG

```python
BasicBlock(id, instructions, label_instructions, leader_reason,
           successors, predecessors, reachable, span)
Edge(src, dst, kind, is_back_edge)
CFG(function, blocks, edges, entry, exit, rpo, back_edges)
```

`kind` is `fallthrough | true | false | jump | return`; `return` edges go to the
implicit `EXIT`, and `ENTRY` is implicit too. `leader_reason` is a short phrase for the UI
(`function entry`, `target of goto L3`, `follows conditional jump`, `follows return`, …).

Three decisions the later passes depend on:

* **Labels are not instructions.** A `label` opcode only marks a leader, so it is absorbed
  into the block it names and never appears inside one. The block keeps it in
  `label_instructions` so `linearize()` can re-emit it — a jump in a linearized function
  would otherwise have nothing to land on.
* **Unreachable blocks are kept** with `reachable=False` rather than deleted. Dead-code
  analysis has to *see* unreachable code in order to explain it.
* **`rpo` is reverse postorder from the entry block** and covers reachable blocks only.
  A back edge is an edge to a node still on the depth-first stack; it is what identifies
  loops.

`linearize()` re-emits a function as a flat instruction list in block layout order, and it
must reproduce the original list exactly for a freshly built graph. Whenever a pass has
deleted a block, the fall-through successor is no longer the next block in layout, so
`linearize()` inserts an explicit `goto` **after** the block whose fall-through it repairs.

### 4.9 Data-flow analysis

All three analyses are the **same worklist algorithm** with different problem definitions, so
they share one convergence guarantee, one trace format, and one rule about dead code. A
problem supplies five things — `direction`, `boundary`, `initial`, `meet`, `transfer` — and
the engine (`opticode.analysis.solver`) does the rest.

```
DataFlowProblem(name, direction, cfg, boundary, initial, meet, transfer, render)
Solution(name, direction, block_in, block_out, iterations, trace, trace_truncated)
```

Three engine decisions are load-bearing:

* **Only reachable blocks are solved.** An unreachable block keeps the initial value and is
  never a neighbour of a reachable one, so dead code cannot invent a fact. Unreachable
  blocks are *absent* from `block_in`/`block_out` rather than present-with-a-default, so a
  caller cannot mistake dead code for an answer.
* **Seeding order is reverse postorder going forward and postorder going backward.** Both
  approaches a definition from the side the facts flow from, which converges in far fewer
  passes. Re-queued neighbours go to the back of the queue in that same order, so the whole
  traversal is a function of the CFG alone and the trace is reproducible run to run.
* **Termination is asserted, not assumed.** The engine stops at `MAX_ITERATIONS` and raises
  `SolverError` rather than spinning. Reaching that bound means a transfer function is not
  monotone, which is a compiler bug worth surfacing instead of hanging the request; the
  pipeline turns it into an internal-error diagnostic.

The iteration trace is capped at `MAX_TRACE_STEPS = 200` because it exists to drive a stepper
UI that only ever shows the first few rounds. `iterations` is always the true count, and
`trace_truncated` says whether the trace was cut.

The trace lives on `Solution`. The pipeline reports per-function `iterations` rather than
shipping three full traces per function, because a loop-heavy function can consume a
large share of the response for data no client renders yet. The stepper will need the
trace, so this is a deliberate omission rather than a finished design — when it lands it
belongs behind a request parameter.

#### Liveness (backward)

A variable is live at a point when some path from it reaches a read without an intervening
write. With `OUT[EXIT] = ∅`:

```
OUT[B] = ⋃ IN[S]          for every successor S of B
IN[B]  = USE[B] ∪ (OUT[B] \ DEF[B])
```

The lattice's ⊥ is ∅ and its meet is plain set union. `USE[B]` is the set of names read
before being written *in the same block*, so `x = 1; return x` does not count `x` as
use-before-def. Both fall out of one backward walk per block, which is also how per-instruction
`live_in`/`live_out` come for free from the converged block.

#### Reaching definitions (forward)

A definition reaches a point when every path to it passes through that definition and
nothing later has overwritten the name. With the boundary at entry:

```
OUT[ENTRY] = { PARAM(v) : v ∈ params } ∪ { UNDEF(v) : v ∈ declared locals }
IN[B]      = ⋃ OUT[P]         for every predecessor P of B
OUT[B]     = GEN[B] ∪ (IN[B] \ KILL[B])
```

The ⊥ is ∅ and the meet is union. Three details that are easy to get wrong:

* `GEN[B]` keeps only the **last** definition of each name in `B`. A block that writes `x`
  twice generates just the second, because the first is overwritten before the block's exit.
* `KILL[B]` includes `PARAM(v)` and `UNDEF(v)` for every name `B` writes. Boundary
  definitions are not written by any instruction, so a scan of instruction definitions alone
  would let them reach forever. They stay in `IN` at entry, which is what makes a read
  *before* the first write still report `UNDEF`.
* `UNDEF(v)` means "a local nothing has assigned on this path". This is the static counterpart
  to the interpreter's `uninitialized_reads`: the same program fact, found without running.

Def-use chains are derived from the solved block states by one forward walk per block, which
keeps them consistent with the block fixed point — a use can never be handed a definition the
block-level analysis had already killed.

#### Constant propagation (forward)

The domain is a three-point flat diamond:

```
      ⊤                      no information yet
     / \
CONST(a) NAC                provably a    /    not a constant
     \ /
   (join of different constants)
```

```
IN[ENTRY] = { v ↦ NAC : v ∈ variables }    nothing is known before execution
IN[B]     = ⋃ IN[P]
OUT[B]    = IN[B][GEN ops]                  each instruction rewrites what it knows
```

`CONST(a) ⊓ CONST(b) = NAC` for `a ≠ b` is the whole rule: two branches that both assign `5`
stay known, two that assign `5` and `6` come out unknown. Values are tagged with their MiniC
type, so `CONST(5)` (int) and `CONST(5.0)` (float) never meet into a value true of neither.

The instruction transfer folds `copy`, `binary`, `unary`, `itof`, and `ftoi` when their
operands are known, and returns NAC when it cannot:

* `call` → NAC, because a return value depends on arguments, global state, and callees.
* `scanf` → NAC, because input is exactly what is not known at compile time.
* division or modulo by a constant zero → NAC, because it **traps** and has no value.
* a float result that is infinite or NaN → NAC, rather than a number the program could not
  have produced.

Folding goes through `opticode.semantics.arith`, the same module the interpreter uses, so
"this expression folds to 5" and "this expression evaluates to 5" cannot drift apart.

### 4.11 Dead and unreachable code

`opticode.analysis.findings` turns the data-flow facts above into a list of `Finding`s.
It changes no code: every finding is an explanation with an `action` saying whether
deleting it would be safe, and `will_be_removed` findings are exactly the ones a later
optimizer pass is allowed to act on.

```python
Finding(id, kind, severity, function, message, explanation, action, span,
        evidence, instruction_ids, ast_node_id, block, kept_reason, duplicate_of)
```

* `kind`: `unreachable_code | conditionally_unreachable | dead_assignment |
  unused_call_result | unused_read_result | use_before_initialization | missing_return |
  constant_condition | constant_division_by_zero`.
* `action`: `will_be_removed | kept | informational`. `will_be_removed` means the analysis
  can prove deletion is unobservable; `kept` means the statement looks dead but has a side
  effect or a possible trap, and `kept_reason` says which.
* `evidence`: spans with a one-line note each — the `return` that cut the path, the
  reassignment that overwrote a value, the comparison that made a branch dead.
* `AnalysisReport` adds `summary` (count per kind), `unreachable_blocks`, and
  `dead_instruction_ids`. Findings are sorted by position, so two runs are byte-identical.

The API payload is `analysis`, an object rather than a per-function map: a finding is a
statement-level claim that may cite several blocks, and keying by function would force a
choice that the diagnostic's own `function` field already makes.

#### Unreachability

A block is **structurally unreachable** when no predecessor reaches it at all. Its first
statement is reported as `unreachable_code` (warning), and the terminator of the block
that precedes it — `return`, `break`, `continue`, or `goto` — is quoted as evidence. The
loop back edge that `while` lowers to carries the loop's own AST node and is deliberately
excluded, so an `if (0)` body is flagged without also flagging the user's `while`.

A block is **conditionally unreachable** when constant propagation proves an incoming edge
never runs. Reachability is then recomputed by BFS from the entry over the edges the
constant facts leave standing, and only the blocks that fall out are reported. That is why
`while (1)` with a `break` reports nothing after the loop: the `break` puts the false edge
back, and the tail stays reachable. `if (0)` bodies and the tail of a `while (1)` with no
exit are reported as `conditionally_unreachable` (warning).

#### Dead stores

An assignment is dead when its destination is not in `live_out` of its block. Three things
keep that from being a lie:

* **Statement grouping.** Lowering gives one source statement several instruction IDs, and
  the copy that lands the value is not the expression that computed it. Instructions are
  grouped by the innermost AST `Stmt` that produced them, so `int y = x;` is one statement
  with one finding even though the copy and the expression carry different node IDs.
* **Producer closure.** A dead-looking statement may still be the only user of a value whose
  *definition* has effects: a `printf`, a `scanf`, a call, or a division that traps. The
  analysis walks backwards through the def-use chains to the producers of the statement's
  operands and keeps the statement if any of them can print, read, call, or trap. When both
  apply, the trap wins. `int z = 3 / d;` is therefore reported but marked `kept`, not as a
  deletion.
* **No double reporting.** Statements in unreachable blocks are reported once, as
  unreachable. They are not also reported as dead stores.

A value that is overwritten before it is read is a dead store (`W-ANL-003`); a variable that
is never read at all is `W-SEM-002`'s job, so the analysis records it with
`duplicate_of="W-SEM-002"` and emits no diagnostic of its own. The same applies to
`W-SEM-003` (missing return) and `W-SEM-004` (division by zero). One fact, one diagnostic.

#### Other findings

* `use_before_initialization` (`W-ANL-004`) — a read whose only reaching definition is
  `UNDEF`, with the same "some other path defines it, so this one is not listed" rule the
  data-flow payload uses.
* `missing_return` (`W-ANL-005`) — an `int` function with a feasible path to the end that
  returns no value. `main` and `void` functions are exempt, and a path that is already
  unreachable does not count.
* `unused_call_result` / `unused_read_result` (`I-ANL-001` / `I-ANL-002`) — a call or a
  `scanf` whose value is discarded. Informational: the call stays.
* `constant_condition` (`I-ANL-003`) and `constant_division_by_zero` (`W-ANL-006`).

### 4.12 Execution outcome

```python
ExecutionOutcome(status, return_value, output, steps, uninitialized_reads,
                 message, stopped_at, entry_function, max_depth_reached, traps)
```

* `status`: `ok | trap | timeout | input_exhausted | stack_overflow`. Traps, exhausted
  input, and stack overflow are *outcomes*, not exceptions, so a caller always gets a
  result back.
* `uninitialized_reads`: names read before any write, in first-read order. The value is `0`
  and the run still succeeds — MiniC leaves such values indeterminate.
* `same_observable_behaviour_as()` compares `status`, `return_value`, `output`, and
  `traps`. `steps` is excluded because an optimization may legitimately do less work, and
  `uninitialized_reads` is excluded because a user cannot see it in the output.

Arithmetic is never implemented in the interpreter: every operator goes through
`opticode.semantics.arith`, the same module the constant folder uses, so an interpreted
program and an optimized one cannot disagree about what `-7 / 2` means.

### 4.13 Provenance

Two identifiers make TAC explainable, and the distinction matters:

* `ast_node_id` — the node the instruction was produced *for*. A copy that assigns a
  lowered value points at the assignment, so the UI can highlight the statement.
* `operand_origin_ids` — the nodes that produced each *operand*. A binary instruction
  points at its two operand expressions.

This split is what keeps the no-duplication invariant checkable: every AST expression node
appears in exactly one instruction's origins (or is referenced directly as a literal or
variable), so a source expression can never be evaluated twice.

## 5. Error strategy

* A user mistake becomes a diagnostic; the stage returns whatever it has.
* The pipeline halts after a stage that produced an **error**. Warnings do not stop it.
* Lexical and syntax errors are recovered from so several are reported at once; the
  number of reported errors is capped to keep the UI readable.
* Any unexpected exception is caught at the stage boundary and converted to
  `E-INT-001` with the exception type and message only.

## 6. Optimization strategy

Passes operate on TAC/CFG, never on raw text. The observable behaviour of a program is
**printed output, consumed input, return value, and traps**. An optimization must
preserve all four. Nothing that may `print`, `read`, `call`, `return`, jump, or trap is
removed or reordered, and loops are never deleted.

Verification runs the TAC interpreter on the original and the optimized IR and compares
status, return value, and output. If they differ the optimized result is discarded and
an internal-error diagnostic is returned instead of shipping a wrong answer.
